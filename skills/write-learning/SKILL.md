# Learning Content Writer

Write and refine language for learning resources: online courses (authored in Rise), knowledge checks, course descriptions, learning pathways, and the copy that announces them.

## Voice and Style: see the Mellonhead Writing Guide

All voice and style rules: `/writing-guide.md` at the project root (canonical). Tone characteristics, signature moves, dash rules, jargon, generalizations, hype, overused structures, edit checklist, cross-section review, and word swaps live there. Always apply those first.

This skill adds only what's specific to learning content: the naming rule for anything staff read (§0), Rise authoring conventions, course structure, knowledge check feedback framing, and the working modes for course descriptions, learning pathways, and announcement copy.

---

## 0. Naming What You Made (hard rule for anything staff read)

**Ruling, MQ 2026-08-24.** Copy that goes out to people names things the way the reader would name them. Never the tool we built it in. Never an acronym the reader was never taught.

**Never name the authoring tool.** Rise, Articulate, Storyline, Gamma, Camtasia, Cluso, SCORM. Nobody takes a Rise course. They take an **online course**. The tool is our production detail and it means nothing to the person opening the link.

**Never use production shorthand.** VILT, ILT, QRG, KC, SME, WBT, LMS, WIIFM. These are how we talk to each other while building. A staff member reading an email should not have to decode them.

| Don't write | Write |
|---|---|
| the Rise course, this Rise module, the Articulate course | the online course |
| VILT, VILT session | virtual workshop (or "live session on Zoom") |
| ILT | in-person workshop |
| QRG, Quick Reference Guide | reference guide |
| KC | knowledge check (spell it out) |
| async module, asynchronous learning | a course you take on your own time |
| the SCORM package, the LMS | the actual system by name ("Workday Learning"), or "the learning site" |
| the Gamma, the Gamma deck | the slides |
| self-paced, e-learning | on your own time, online course (see `/writing-guide.md` §9.1) |

### Where this applies

Anything a learner, a manager, or a staff member opens: announcement and enrollment emails, prep emails, calendar invites, chat and intranet posts, catalog and LMS descriptions, course introductions, reference guide covers, slide text, reminders, sign-offs.

### Where the internal names are still correct

Backstage documents where the tool or format is the actual subject: build instructions, publish trackers, design briefs, task lists, proposal scope tables, facilitation guide production notes, and the authoring conventions in §1 of this skill. Naming Rise in a build note is precise. Naming it in an email is jargon.

**The test:** would someone who has never worked in L&D know exactly what they are being asked to open, and when? If the word only makes sense to someone who builds training, replace it with what the reader experiences.

## Working Modes

Determine which mode applies based on the request:

### Mode 1: Writing new content
Drafting from scratch or building out a section. Apply voice and tightening rules as you write. If the user has shared surrounding sections for context, flag any cross-section issues (repetition, terminology gaps) in your response. Don't run a full review unless asked.

### Mode 2: Editing / revising
Refining existing content. Ask: **"Are we tightening this block, or reviewing across sections?"**
- **Tightening a block:** Run the Edit Checklist (Cut, Convert, Clarify) from `/writing-guide.md` §4.
- **Reviewing across sections:** Run the Cross-Section Review checklist from `/writing-guide.md` §5. Requires the user to share all relevant sections.

### Mode 3: Full review
Final check before handoff. Run both passes in sequence:
1. **Edit Checklist** (block-level tightening)
2. **Cross-Section Review** (across all sections)

Report findings from each pass separately so the user can address them in order.

### Mode 4: Course descriptions
Catalog-ready descriptions for an LMS or program overview. See §3 below.

### Mode 5: Learning pathway / training plan
Recommended schedule for completing a multi-course program. See §4 below.

### Mode 6: Announcement and enrollment copy
The email, invite, or post that tells staff a course or workshop exists and what to do before it. See §7 below. Apply §0 without exception. Other skills route here for this copy: `/facilitation-guide` for the prep email, `/project-tasks` and program leads for launch announcements.

## 1. Online Course Content (authored in Rise)

### Structure

```
Learning Objective (what they'll be able to DO)
↓
Hook (why this matters to them)
↓
Core Content (chunked into 3-5 key points)
↓
Example / Demonstration
↓
Practice Activity
↓
Key Takeaway (one sentence)
```

### Language Rules (learning-specific)

- Write in second person ("You will." not "Learners will.").
- Keep paragraphs to 2-3 sentences max.
- One idea per screen or section.
- Use "Let's." sparingly to create partnership feeling.
- Front-load the value: lead with what they GET, not what they'll DO.

(All universal voice rules from `/writing-guide.md` also apply.)

### Rise Authoring Conventions

When building in Articulate Rise:

- Start lessons with **text blocks**, not header+text. Rise has a built-in lesson header (title and optional image) at the top of every lesson. A header block right underneath is redundant.
- **Header blocks earn their place** when you need to signal a shift in section or topic *within* a lesson (e.g., moving from "Where the policy is clear" to "The decision framework"). Not as lesson openers.
- One idea per block. If a block is doing two things, split it.

### Teaching Frameworks and Checklists

When introducing a multi-step framework or checklist that learners will practice in full, address the "am I really going to do this every time?" reaction early. Learners will think it before you say it. Frame the goal as internalization, not compliance:

> "The goal isn't to run this checklist every time you use AI. It's to internalize what good review looks like so these steps become second nature."

Say it once, right when the framework is introduced. Repeating it later undermines the content. Saying it too early (e.g., in the course description) risks learners dismissing the material before they've seen it.

### Before / After

**Before:**
> "In this module, participants will learn about the various components that make up an effective prompt and how these components work together to produce better outputs from AI systems."

**After:**
> "Better results from AI start with how you ask. In this module, you'll learn the four parts of a strong prompt and practice building your own."

## 2. Knowledge Check Feedback

Full rules in `/writing-guide.md` §7.2. Learning-specific notes:

- Feedback follows immediately after the learner's selection. Don't restate the question. They just read it.
- Per-option feedback on capstone questions can be 3 to 4 sentences. Each option's feedback shows the consequence of that choice.
- Combined feedback (single feedback for all responses) is appropriate when all options are defensible and the lesson is about tradeoff awareness, not a single correct answer.

| Too long | Right length |
|---|---|
| "Trust in each of these relationships depends on something AI cannot provide: your independent judgment and operational perspective. The idea that only the final document matters misses a key point. An advisory that sounds confident but lacks operational depth can mislead member banks in ways that are harder to catch precisely because the language is polished. How the analysis was developed affects what makes it into the document." | "An advisory that sounds confident but lacks operational depth can mislead member banks in ways that are harder to catch precisely because the language is polished. How the analysis was developed affects what makes it into the document." |

## 3. Course Introduction / Overview

The course introduction is the first thing learners see in Rise, before any lesson begins. It sets expectations and gets out of the way. The lessons do the real work.

### Structure

```
Description (2-3 short paragraphs)
├── Acknowledge what they've already done or know
├── Name the gap this course fills
├── Close escape hatches (preempt opt-out thinking)
└── Frame what this course IS about (not just what it covers)

Outcomes (bullet list)
├── Rewrite formal objectives as things they'll walk away with
├── Use plain language, not Bloom's taxonomy
└── 3-5 bullets max

Course Structure (table)
├── Lesson name | What to expect | Time
└── Keep descriptions to one line each

Time estimate (one line)
```

### Language Rules

- Text-only block. The course title already appears in the Rise course header / banner.
- Acknowledge prior learning first. If this course follows another, say so. Avoids the "another compliance course" feeling.
- Close escape hatches early. If learners can mentally opt out ("I don't even use AI" or "this doesn't apply to me"), address it directly.
- Rewrite objectives as outcomes. Formal objectives stay in your design documents. Learners care about what they'll walk away with, not which Bloom's verb you used.
- Keep it short. Three paragraphs for the description, max.
- The "What to expect" column describes what the learner does in the lesson, not what they will learn. Naming a section's reveal on the intro screen spends it (reviewer finding 2026-09-03, Summarizing course F4).

### Before / After

**Before:**
> "Welcome to this course on AI ethics and responsible use. In this course, you will learn to recognize that ethical judgment in AI use is an extension of existing professional decision-making, apply core competencies as a lens for making ethical decisions, distinguish between policy violations and ethical dilemmas, and analyze ethical dilemmas using Kidder's framework."

**After:**
> "You've completed ABA's AI policy training. You know what's allowed and what isn't. This course picks up where policy leaves off.
>
> Many of the AI decisions you face at work aren't clear-cut. The policy covers a lot, but it can't anticipate every situation. When you're in that gray area, your judgment matters.
>
> This is not about whether to use AI. It's about how to use it well."

## 4. Course Descriptions (Mode 4)

Catalog-ready summaries for an LMS or program overview. Short, engaging, make learners want to take the course.

### Principles
- Start with what the learner gets, not "Participants will."
- Use second person ("you'll"), conversational tone.
- Structure: hook or context sentence, what you'll do in the course, payoff or outcome.
- One paragraph for catalog listings. 2-3 short paragraphs for detailed views.
- Avoid listing individual features or tools when a thematic summary works better.
- For program-level descriptions, frame the full learning journey rather than listing each course.

### Cut these from a catalog description
A description says what the learner *gets*, not how the course is built. Cut on sight:
- **Scenario mechanics.** Dataset names and counts ("four datasets"), artifact specifics ("one-page readout," "messy export"), fiscal-year or persona labels ("FY27 budget," "the events lead"). These live in the facilitation guide, not the catalog.
- **Audience qualifiers.** "at ABA," "even for people never trained as analysts." Descriptions travel across catalogs; keep them role-agnostic unless the audience *is* the hook.
- **Throat-clearing setup lines.** "The hard part usually isn't the tool." Get to the point.
- **Restated payoffs.** If a sentence says the value a second time in new words ("the approach carries over to any data you bring"), cut it once the point is made.

Default to **two short paragraphs**. Add a third only when it carries real structure (e.g., the Part 1 / Part 2 split).

### Sub-pattern: blended course description set (Part 1 + Part 2)

When a course pairs an online Part 1 with a hands-on Part 2, write three descriptions. Each has a distinct job. ("Self-paced" and "hands-on" below are our labels for which description you are writing. Per §0, the words in the description itself are "online course" and "workshop.")

- **Part 1 (self-paced):** Open with the problem or why it matters. Then one paragraph on what the self-paced course introduces and how it sets up Part 2. ~2 short paragraphs.
- **Part 2 (hands-on):** Open with the failure or frustration of doing this *without* the skill. One paragraph on what they practice across the workshop. Then one short line naming what they practice on: if learners bring their own work, say so and give the fallback ("or use a prepared example").
- **Whole course:** The "if you have X and Y" hook, the approach in one paragraph, then the Part 1 / Part 2 structure in two lines.

**Hands-on note:** Name what learners practice on. "A real dataset and business problem that you bring, or use a prepared example" is a more useful catalog detail than describing the provided scenario, and it reframes the value from "practice our example" to "bring your own."

**Exemplars:** Full example descriptions (catalog listing, detailed listing, and the Turning Data Into Stories Part 1 / Part 2 / whole-course set) live in `references/course-description-examples.md`.

**Side-by-side comparison mode:** When writing descriptions, offer multiple versions in a markdown table (Original | Version A | Version B) so the user can compare side-by-side and choose or mix for stakeholder review.

## 5. Learning Pathway / Training Plan (Mode 5)

Recommended schedule for completing a multi-course program. Summary table, week-by-week detail, and optionally a calendar-blocking prompt for learners.

### Summary table structure

| Week | Date | Course | Practice |
|------|------|--------|----------|
| 1 | Day, Date | Course name | One sentence describing what to practice |

### Design principles
- Sessions should fit within realistic time blocks (30 min or 1 hour).
- Account for reading time, video time, activity time, and practice time.
- Spread intensive content (hands-on tool lessons) across multiple weeks.
- Group thematically related courses (e.g., communication tools together, data tools together).
- Lighter courses can share a session. Heavier ones get their own.
- Check for holidays and account for the release date when setting specific dates.

### Week-by-week detail
Each session gets a heading with the day, date, and duration, followed by a short paragraph explaining what the session covers and what to practice. Keep it practical and encouraging.

### Calendar-blocking prompt (for learners to paste into Copilot)
- Use numbered events (not bullets) so the AI doesn't skip any.
- State the total count upfront ("Block the following 9 events.").
- Include duration per event.
- Include a description / agenda per event (e.g., "Self-paced learning. Complete the course and try the activities.").
- Set reminder preferences.
- End with a validation step: "After creating all events, confirm that exactly N events were created and list the dates."

## 6. How-To Guides and Job Aids

### Structure

```
Title: [Action verb] + [Outcome]
Instruction: [One direct sentence]
Key inputs: [Ultra-short bullets, fragments OK]
Insight: [One line that reframes HOW to think about it]
Examples: [Example / Not pattern]
```

### Language Rules
- Start with a direct imperative ("Tell the AI." not "You should tell the AI.").
- Use ultra-short bullet fragments for inputs and steps.
- Include ONE standalone insight line that shifts thinking.
- Use "Example / Not" pattern to show right vs. wrong approach.
- Every word must earn its place. If it can be cut, cut it.

### Exemplar

> **Clarify Emails**
>
> Tell the AI which emails you want in plain language:
>
> - Who sent them
> - What they're about
> - Roughly when
>
> The AI uses language to understand context and intent, not just keywords.
>
> **Example:** "Emails from John Doe in Q4 about the board presentation"
> **Not:** "emails with the word 'board'"
>
> **Example:** "Messages from my direct reports this month regarding budget approvals"
> **Not:** "emails containing 'budget'"

### Pattern: Ultra-Short Bullets
Strip bullets to their essence. No articles, no verbs if not needed.

| Don't | Do |
|---|---|
| You should specify who sent the emails you're looking for. | Who sent them |
| Include information about what the emails are about. | What they're about |
| Provide an approximate timeframe for when the emails were sent. | Roughly when |

### Pattern: The Standalone Insight
One sentence that changes how the reader thinks about the task.

> "The AI uses language to understand context and intent, not just keywords."

This line does the heavy lifting. It explains WHY the examples work without over-explaining.

### Pattern: Example / Not
Show the right way, then contrast with the limited way.

| Example (rich context) | Not (keyword thinking) |
|---|---|
| "Emails from John Doe in Q4 about the board presentation" | "emails with the word 'board'" |
| "Messages from my direct reports this month regarding budget approvals" | "emails containing 'budget'" |

## 7. Announcement, Enrollment, and Prep Copy (Mode 6)

The email or post that tells staff a course or workshop exists. It is read once, fast, usually on a phone, by someone who did not ask for it. Its whole job is: what is this, why should I care, what do I do, by when.

### Structure

```
Subject line: what it is + when (no clever framing)
├── One line of why this matters to them (not to the org)
├── What it is: one sentence, in reader words (see §0)
├── What to do: numbered steps, each with a verb and a link
├── When: the specific date or deadline, bolded
└── Brief personal sign-off
```

### Rules

- **Apply §0 first.** "Reserve 45 minutes for the online course before Thursday's virtual workshop" is the sentence. Not "complete the Rise module before the VILT."
- **Lead with the reader's stake, not the program's.** Not "As part of our AI enablement rollout." Try "Thursday's session is hands-on, so the 20 minutes beforehand is what makes it worth your time."
- **One ask per email.** If there are two things to do, number them and say how long each takes.
- **Time estimates are a courtesy and they earn compliance.** Give them for every step.
- **Say the deadline as a day, not a duration.** "Before Thursday," not "within 48 hours."
- **Bold "Action required" only when action is actually required.** If it is informational, do not dress it up.
- **Sign off as a person.** A name, not a department.
- **No hype.** §3.5 of the writing guide applies. "Excited to launch" adds nothing.

### Before / After

**Before:**
> "Subject: AI Foundations Rise Course Now Live in the LMS
>
> As part of our ongoing AI enablement initiative, we are excited to announce that the AI Foundations self-paced Rise course is now available. Please complete the course and associated KCs prior to your scheduled VILT. The QRG will be distributed following the session."

**After:**
> "Subject: 20-minute course to finish before Thursday's workshop
>
> Thursday's workshop is hands-on. You will be working with your own files, not watching a demo. The online course below covers the basics so we can skip them in the room.
>
> **Before Thursday:**
> 1. Take the online course (20 minutes, link)
> 2. Bring one email thread or document you would normally spend too long on
>
> You will get a reference guide afterward to keep.
>
> Mariena"
